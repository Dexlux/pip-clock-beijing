# pip-clock-beijing

北京时间和时 PiP 悬浮时钟,可用于抢购场景。

## 功能

- **北京时间**: 使用 `Intl.DateTimeFormat` 指定 `Asia/Shanghai` 时区,与设备时区无关
- **网络对时校准**: 启动时从多个源(自建大阪 / timeapi.io / Cloudflare / 1.1.1.1 / 腾讯)对时,按"不确定度"选源并加权;**设备时钟本来就准就不去动它**(公网源精度只有 `RTT/2`,硬修反而更差),状态栏用大白话说"现在准不准"
- **PiP 小窗**: Canvas 通过 `captureStream()` 转为视频流,支持点击按钮进入画中画模式
- **毫秒显示**: 时间显示到毫秒精度,方便抢购卡点
- **粒子特效背景**: 使用 canvas 绘制粒子网络背景

## 自建毫秒源

国内网络常常连不上 `timeapi.io`,只剩整秒源时精度天花板是 ±0.5 秒,抢票不够。所以在甲骨文大阪的机器上自建了一个毫秒源(该机 `chrony` 系统误差 0.12ms):

```
GET https://t.infiniteai.asia/now
→ {"t":1794575294.286,"src":"oracle-osa"}
```

- nginx `$msec` 直接给出秒+毫秒,无时区歧义
- 响应头带 `Access-Control-Allow-Origin: *` 和 `Cache-Control: no-store`,浏览器可跨域直取
- 域名是「仅 DNS」(灰云),不走 Cloudflare 代理,请求直达源站少一跳
- 站点配置在源站 `/etc/nginx/conf.d/https-newapi.conf` 的 `t.infiniteai.asia` 段,证书由 certbot 自动续期
- 实测:本机到源站 RTT ~120ms → 不确定度 ±61~69ms,连续 5 次校准极差 2.5ms

## 对时算法

- **源与分辨率**: `自建大阪` 和 `timeapi.io` 是真毫秒源(1ms);`Cloudflare`、`1.1.1.1`、`腾讯` 只有整秒精度(1000ms),只作粗校验/兜底,不会冒充毫秒精度
- **采样**: 源间并行、源内串行(毫秒源 5 次、整秒源 3 次),RTT 只算到响应头到达;所有请求带随机防缓存参数
- **聚合**: 单源按 NTP 最小 RTT 窗口(`rtt <= minRtt*2+80`)过滤后取 offset 中位数,不确定度取 `u` 中位数与样本极差/2 的较大者;整秒源是向下截断的,offset 加半个分辨率(`+500ms`)居中后再参与比较
- **跨源一致性**: 共识在最高精度层里算(有毫秒源时不让整秒源的 ±500ms 粒度带歪中位数),各源按 `容差 + 自身分辨率/2` 判定——有毫秒源 400ms、否则 1200ms;若整秒源彼此一致却和毫秒源差 >1.2s(时区错/缓存脏值),以整秒源多数为准并降级粗对时
- **出结果**: 先按分辨率、再按不确定度选源,只与同分辨率且相差 ≤200ms 的源做 `1/u²` 加权平均;偏移保留浮点,不取整
- **跨批次平滑**: 公共毫秒源常常连不上,单次校准随机误差有 ±100ms 量级(实测 `timeapi.io` 连续 5 次极差 178ms);自建大阪源下不确定度降到 ±61~69ms、连续 5 次极差 2.5ms,平滑仍保留但已不是必需。因此保留最近 5 次、20 分钟内的校准结果做逆方差加权合并,离群值(偏离历史 >500ms 且本次精度不足)直接丢弃;系统时钟被外部改动(睡眠唤醒/NTP 跳变)时清空历史,不让平滑把错误值拖住。平滑后连续 5 次校准极差降到 <10ms
- **时钟模型**: 单调锚点 `anchor = {epoch, perf}`,`nowMs() = anchor.epoch + (performance.now() - anchor.perf)`,不受系统 NTP 跳变影响;每帧与 `Date.now()+offset` 比对,漂移 >300ms 自动重建锚点并重校
- **要不要修正(反向门控)**: 估计出的偏差不比它自己的不确定度大时(`|偏差| ≤ u`),这个偏差在统计上无法与 0 区分,按噪声处理**不做修正**。原因是设备自带的 NTP 通常就准到 ±10~100ms,而公网毫秒源精度上限只有 `RTT/2`(实测 ±250ms 量级),硬套一个更差的修正只会让钟变跳。只有 `|偏差| > u` 才按收缩估计 `k = 1 - (u/偏差)²` 补正——`k` 连续,小偏差时趋 0(不动)、大偏差时趋 1(全额补正)
- **完成判据**: 必须拿到毫秒级源且残余误差 ≤400ms 才算"校准完成";已达标后要劣化到 560ms 才掉档(滞回),避免网络抖动让状态在 ✅ 和 ⏳ 之间反复闪
- **文案原则**: 主文案只回答"现在准不准",历史偏差降级为副行小字。因为 `偏移=+28ms`、`已校准 +1.2s` 这类记法会被读成"校准完还差 1.2 秒"(符号方向反直觉)。状态栏四种状态:

  | 场景 | 主行 | 副行 |
  |---|---|---|
  | 设备钟本来准 | `✅ 与标准北京时间一致` | `本机与标准时间相差 Nms，在测量误差 ±Nms 内，未做修正 · 源 X` |
  | 设备钟有偏差 | `🔧 本机原本慢/快 X，已补正` | `现在误差 ±Nms · 源 X` |
  | 有毫秒源但不够准 | `🟡 已对时 · 精度 ±Nms` | `网络较慢，已是最优结果 · 源 X` |
  | 只有整秒源 | `🟡 已对时 · 精度 ±0.5 秒` | `当前网络连不上毫秒源，只能按秒校时 · 源 X` |
  | 全部源失败 | `⚠️ 对时失败（第 N 次）` | `暂时沿用上次校准值 · 30 秒后自动重试` |

  只有首轮采样还没拿到任何结果时才显示 `⏳ 正在对时…`；一旦有结果就绝不回到"校准中"——哪怕精度只有秒级,那也已经是完成状态,不是进行中。

- **canvas 角标**: 与状态栏同步,共五档——`✓ 无需修正`(绿) / `✓ 已补正`(绿) / `🟡 秒级精度`(黄) / `🟡 精度一般`(黄) / `⏳ 对时中`(黄)
- **首屏速度与缓存**: 分两阶段——阶段一每个源只采 1 个样本,1~2 秒就先把可用时间上屏(标"初步"),阶段二补采样本再精化;某源连续 2 次失败即判定本网络不可用并放弃(不再把 5 次超时跑满),单请求超时 3.5 秒。手机连不上毫秒源时,原实现要等 5×6 秒串行超时才回退、且永远卡在"校准中";现在实测 **29 秒 → 1.2 秒**。上次校准结果存 `localStorage`(10 分钟 TTL),二次打开 0.7 秒内就有时间可读,标 `⚡ 沿用上次校准` 后再后台重校
- **调试**: 控制台可读 `window.__clock.state` / `__clock.nowMs`,或 `__clock.calibrate()`、`__clock.probeRaw('timeapi.io')`

## 使用方法

1. 打开页面,等待对时完成
2. 点击"进入小窗"按钮进入 PiP 模式
3. 时钟会悬浮在任何其他 App/网页之上

## 平台支持

- Chrome/Edge/Mac Safari: 完美支持
- iOS Safari: 切到其他 App 时,系统可能冻结后台 JS(PiP 画面可能停住)

## 本地测试

```bash
python3 -m http.server 8080
# 访问 http://localhost:8080
```
